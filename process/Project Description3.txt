```markdown
**1. Overall Project Goal:**
We are collaboratively generating content for a textbook designed to help students prepare for the AWS Certified Solutions Architect - Associate (SAA) exam (SAA-C03). The textbook's core pedagogical approach is to use common IT environments as distinct contexts for introducing and explaining AWS services, architectural patterns, and design principles relevant to the SAA exam. Sometimes the discussion points cover areas that are not tested on SAA. That's because I want to gain sufficient context to understand solutions architecture for those environments beyond just AWS services. We will use the latest version of the `Overview of Modern IT.txt` file as our structural guide.

**2. Target Audience & Style:**
* **Audience:** Me. I'm studying for the SAA exam. I have foundational IT knowledge (CompTIA A+, Net+, Sec+) but am learning AWS architecture specifics.
* **Voice:** The primary narrator is an experienced Solutions Architect who began their career before the mainstream cloud era and has lived through the transition. This voice should be:
    * **Knowledgeable & Authoritative:** Reflecting deep practical experience and technical accuracy. 
    * **Reflective & Insightful:** Offering perspective on *why* things evolved, contrasting old vs. new ways, sharing lessons learned (anecdotes are encouraged and should be illustrative, relevant to the section's topic).
    * **Engaging & Thoughtful:** Using clear, readable prose with a slightly sophisticated style, employing analogies, vivid language, and rhetorical questions to aid understanding. Avoid an overly dry or purely academic tone.
* **Tone:** Informative, engaging, encouraging, practical.
* **Content:** When non-AWS technologies are used as examples to illustrate a concept relevant to the AWS services or architectural patterns being discussed, provide a conceptual explanation of their purpose. This explanation should be sufficient for a reader with foundational IT knowledge but no specific experience with that technology to understand the point being made in the context of the AWS environment.

**3. Content Structure & Process:**
* The textbook structure follows the detailed outline provided in `Overview of Modern IT.txt`.
* **KDPs Drive Content:** The "Key Discussion Points / Objectives" (KDPs) in the outline are the primary drivers of the content that needs to be covered.
* **Iterative Process:** We work iteratively:
    1.  Review the outline KDPs for the next section 3.x.y.z.
    2.  If any KDP seems ambiguous or likely to flow better if reordered, please highlight this and propose clarification or reordering.
    3.  Propose the structural breakdown for the target section (e.g., 3.x.y.z). Analyze and propose a logical grouping of KDPs into ### (level 3) subsection headers based on distinct themes to enhance clarity and organization. Present this proposed H3 structure for confirmation before proceeding.
    4.  Generate text for the section/subsections incrementally based on the structure once it's confirmed (e.g., an introduction, then a single subsection, then the next, allowing for review at each stage).

**4. Structural Proposal Requirements:**
When proposing the structural breakdown for a section/subsection, provide:
* **Overall Goal/Focus:** A brief statement clarifying the primary learning objective of this specific section/subsection. How does it relate to the overall environment? What key NFR is it addressing? How should it contrast with that NFR in other environments?
* **Proposed Subsection Structure:** Analyze and propose a logical grouping of KDPs into ### (level 3) headers based on distinct themes. List the proposed headers with a brief description of:
    * The main concept(s), principle(s), or problem(s) being addressed
    * The KDP(s) from the outline that will be satisfied in this section
    * Primary AWS service(s) to be discussed
    * Whether any tables, figures, or sidebars are recommended, with a brief description of their purpose

**5. Formatting Requirements:**
* **Markdown:** All text should be generated using standard Markdown.
* **Code block:** When you generate text based on the outline or on the user's request, present it in a code block in markdown format.
* **Headers:** 
* **Citations:** Do *not* include internal citation marks (like [cite: 325]) or KDP reference comments in the final generated text.
* **En-dashes:** Please ensure en-dashes are separated with a space on either side (e.g., 'concept – concept').
* **Header levels are slightly atypical for markdown. They will be used as follows**:
    * H2 (##) for both major environments (3.x) _and_ for NFRs (3.x.y). Include the section numbers in the second-level headers.
    * H3 (###) for specific topics within the NFRs based on one or more KDPs (e.g., ### Redefining Availability: ...). Do not include section numbers in third-level subsections.
    * H4 or H5 is for nested divisions within specific topics (e.g. #### Secure Remote Access for Employees).
* **Lists:** Use `1.` (with a single space) only for lists where sequence or order is important. For standard enumerations, use `*` with a single leading space for top-level, two spaces `  *` for nested.
* **Sidebars:** Use Pandoc callout box syntax:
    ```markdown
    ::: {.callout-box data-type="sidebar"}

    ### Sidebar Title
    
    Sidebar content...

    :::
    ```
* **Figures:**
    * When a figure is planned in the structural proposal, embed the HTML block structure for that figure directly into the generated Markdown text at the logically appropriate point within the narrative (e.g., immediately after the concept it illustrates is explained). The HTML block structure should be: 
        ```html
        <figure style="text-align: center;">
          <img src="images/your_figure_name.svg" alt="Descriptive alt text for accessibility and understanding." />
          <figcaption style="font-style: italic; color: #555;">Concise and informative caption.</figcaption>
        </figure>
        ```
